# Supabase 연결 안내

프로젝트: `https://syyfpdcylvumvyrlgezc.supabase.co`

공개용 Publishable key와 주소는 `config.js`에 설정되어 있습니다. 이 키는 비밀 키가 아니며 웹에 포함해 사용하는 값입니다. 데이터 보호는 키를 숨기는 방식이 아니라 로그인·서버의 허용 목록·행 수준 접근 제어로 처리합니다. Secret key, service_role, 데이터베이스 비밀번호는 프런트엔드나 GitHub에 넣지 않습니다.

## 1. 테이블과 권한 만들기

Supabase 프로젝트의 **SQL Editor → New query**에서 `supabase/001_haru.sql` 전체를 실행합니다.

- `haru_members`: 사용할 수 있는 계정의 허용 목록
- `haru_documents`: 계정별 기록 문서, 저장 버전, 최근 저장 시각
- `haru_save_document`: 인증과 허용 목록을 검사하고 저장 버전이 맞을 때만 저장하는 함수

익명 사용자는 테이블을 읽거나 쓸 수 없습니다. 로그인 사용자도 자신의 허용된 기록만 읽을 수 있습니다. 앱의 직접 테이블 쓰기는 허용하지 않고 검사된 함수로 저장합니다. SQL은 반복 실행해도 기존 기록을 삭제하지 않습니다.

## 2. 본인 로그인 계정 만들기

**Authentication → Users → Add user / Create new user**에서 본인이 사용할 이메일과 비밀번호로 계정을 만듭니다. 가능한 경우 이메일 확인(Auto Confirm User)을 완료하세요. 프로젝트 관리자 계정의 로그인과 앱의 로그인 계정은 별개입니다.

비밀번호는 본인이 보관합니다. 개발자나 채팅에 전달하지 않습니다. 이 앱은 공개 회원가입이나 메일 비밀번호 재설정 화면을 제공하지 않으므로, 초기에는 프로젝트 관리자 화면에서 계정을 관리합니다.

프로젝트의 Authentication 설정에서 새 사용자 가입 허용도 꺼둘 것을 권합니다. 앱은 새 회원가입을 제공하지 않고, 가입 기능이 켜져 있더라도 아래 허용 목록에 등록되지 않은 계정은 기록을 사용할 수 없습니다.

## 3. 본인 계정 허용

`supabase/002_allow_owner.sql`의 `REPLACE_WITH_YOUR_LOGIN_EMAIL`을 2번에서 만든 이메일로 바꿔 **SQL Editor**에서 실행합니다. 이메일은 비밀번호가 아닙니다. 계정을 아직 만들지 않았다면 SQL이 오류를 내도록 되어 있습니다.

로그인 계정 생성과 사용 권한 등록이 모두 필요합니다. 사용자 계정을 새로 만들 때에도 이 두 단계를 적용합니다.

## 4. 웹페이지 배포

같은 폴더에 아래 파일을 두고 기존과 같이 정적 웹페이지로 배포합니다.

- `index.html`
- `styles.css`
- `app.js`
- `cloud.js`
- `config.js`

빌드나 별도의 Node 서버는 필요 없습니다. GitHub Pages의 HTTPS 주소로 실행할 수 있습니다. 이 파일들은 아직 GitHub에 자동 업로드하거나 배포하지 않았습니다. 기존 CEO Diary의 루트 파일을 덮어쓰려면 먼저 백업하거나 별도 저장소·하위 폴더를 사용하세요.

로컬 검증은 이 폴더에서 `python3 -m http.server 8020 --bind 127.0.0.1`로 실행합니다. 서버가 중지되거나 새 실행 환경이 복원되면 다시 시작합니다. 이미 격리된 작업 환경이므로 별도 Git worktree는 필요 없습니다.

## 5. 첫 사용 및 기존 기록 이전

1. 웹앱에 2번에서 만든 이메일·비밀번호로 로그인합니다.
2. 처음에는 서버 기록이 비어 있습니다. 기존 브라우저 기록을 자동으로 올리거나 서버 내용을 덮어쓰지 않습니다.
3. 같은 브라우저·같은 웹사이트 주소에 기존 기록이 있으면 **계정 · 동기화 → 기존 브라우저 기록 가져오기**를 사용합니다. 서버 기록 전체를 교체한다는 확인 후 저장합니다. 기존 브라우저 원본은 삭제하지 않습니다.
4. 다른 주소나 브라우저의 기록은 이전 주소에서 JSON 백업을 다운로드하고 로그인한 새 앱의 **백업 → 복원**으로 가져옵니다. 현재 계정의 서버 기록 전체를 교체하므로 이미 기록이 있다면 먼저 백업하세요.
5. ‘서버 저장 완료’를 확인한 후 다른 브라우저에서 같은 계정으로 로그인해 기록을 확인합니다.

## 저장 상태와 동시 수정

- 서버 저장 중: 변경을 계정별 기기 임시 저장소에 보관하고 서버에 보내는 중입니다.
- 서버 저장 완료: 서버가 새 저장 버전을 반환했습니다.
- 서버 미저장: 네트워크 실패 등으로 저장이 확인되지 않았습니다. 이 기기의 변경은 임시 보관되며 재시도할 수 있습니다.
- 다른 기기 변경: 다른 브라우저에서 먼저 저장했습니다. 자동으로 덮어쓰지 않습니다. 현재 기록을 백업한 뒤 서버 기록을 불러오거나, 명시적으로 내 변경으로 교체할 수 있습니다.

계정별 문서에는 현재 5MB 크기 제한이 있습니다. 이는 Supabase 무료 플랜의 전체 DB 한도와 별개인 앱의 초기 보호 한도입니다. 기록이 커지면 개별 기록 단위 테이블로 나눌 수 있습니다. 전체 문서를 저장하는 초기 개인용 구조이므로 충돌 시 개별 문장을 자동 병합하지 않습니다. 기기에 미저장 기록이 있으면 새로 로그인할 때 복구합니다. 계정 A의 임시 기록을 계정 B에 자동 적용하지 않습니다.

화면이 열려 있을 때 약 45초마다 가벼운 버전 정보만 확인하고, 변경이 있을 때만 본문을 읽습니다. 입력 중인 폼이나 열린 편집창이 있으면 자동 새로고침을 피합니다. 다른 기기에서 변경한 내용을 즉시 확인하려면 계정 메뉴의 서버 상태 확인을 누릅니다.

로그인 갱신용 토큰은 탭의 sessionStorage에 저장하며 비밀번호는 저장하지 않습니다. 브라우저 탭을 닫으면 재로그인이 필요할 수 있습니다. 서버 미저장 데이터와 기존 로컬 데이터는 해당 기기에 남을 수 있으므로 공용 기기는 피하세요. 이 버전은 저장 데이터의 종단 간 암호화를 제공하지 않습니다.

## 검증 범위

- 실제 PostgreSQL 엔진(PGlite)에서 RLS·허용 목록·익명 접근 거부·직접 쓰기 거부·버전 충돌·반복 SQL 실행을 검증했습니다.
- 브라우저 통합 테스트에서는 Supabase API를 모사해 로그인, 서로 다른 두 브라우저의 같은 계정 기록, 계정 분리, 오프라인 복구, 응답 유실 재확인, 동시 수정 충돌, 입력 보존, 모바일을 검증했습니다.
- 실제 프로젝트에 SQL을 실행하거나 실제 사용자로 로그인하는 작업은 이 검증과 별개입니다. 현재 클라우드 실행 환경의 프로젝트 도메인 연결은 프록시 정책으로 차단되어 실제 Supabase 연결은 아직 검증하지 못했습니다.

코덱스 실행 환경의 허용 도메인 초안에는 해당 프로젝트 호스트를 추가해두었습니다. 이 작업 환경에서도 직접 연결 테스트하려면 환경 설정에서 초안을 검토·저장하고 게시한 뒤 다시 연결을 확인해야 합니다. 이 설정은 GitHub Pages를 쓰는 사용자 브라우저의 접근 권한과는 별개입니다.

## 선택적 개발 검증

- SQL: Node에서 `@electric-sql/pglite`를 사용할 수 있는 환경에서 `node tests/sql-security.cjs`
- 브라우저: `playwright`와 Chromium을 사용할 수 있는 환경에서 서버를 시작한 뒤 `node tests/cloud-sync.cjs`
- `HARU_TEST_URL`, `CHROMIUM_PATH`로 테스트 주소와 Chromium 실행 파일 경로를 바꿀 수 있습니다.

테스트에는 실제 사용자 비밀번호·토큰을 사용하지 않습니다.
